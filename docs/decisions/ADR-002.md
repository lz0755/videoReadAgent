## 1. 背景与依赖兼容性核验

按照项目计划书 §6.4 与 Vibe Coding 指南第七节，M1.5 的目标是在大规模建设 M2 完整媒体/作业持久化、M3 SQLite FTS5/完整索引、M4 多轮 Agent 之前，优先打通一条**真实视频文件 → 抽帧与音轨提取 → 转写 → 视觉观察 → 内存中文 bigram+英文检索 → 带引用 QA → 诊断报告**的端到端垂直切片，尽早暴露真实媒体时间戳、多图边界、提示词与预算集成问题。

### 1.1 Python 3.14.6 媒体与 ASR 依赖核验（解除 ADR-001 风险项）

ADR-001 曾标注在 Python 3.14.6 环境下引入 `PyAV` 与 `faster-whisper` 存在 wheel 兼容性风险。本阶段在 Windows 11 + CPython `3.14.6` 实测确认：
- `av==19.0.2`：wheel 正常安装，真实解封装与帧解码在合成夹具（F01–F04）及 3 段真实 D0 1080p H.264 视频（`vg_pr10_start`、`ocr_941`、`ocr_750`）上全部通过；
- `faster-whisper==1.2.1`：wheel 正常安装，薄适配器采用延迟导入（零 import-time 权重下载）、强制 `vad_filter=False` 与 `local_files_only=True`，未提供本地权重目录时明确返回 `DEPENDENCY_MISSING`；
- `ffmpeg` / `ffprobe` `8.1.2-essentials_build`：音轨提取与 `audio_offset_ms` 探测实测通过。

> 注：Video-MME v2 的 HEVC（H.265）视频未进入 M1.5 3 段切片清单，将在 M2 媒体加固阶段针对 `vmme_001` / `vmme_087` 等样本专项实测 PyAV 解码。

### 3.2 真实媒体暴露的关键工程边界（M1.5 的直接收益）

1. **NTSC 非整数帧率（29.97 fps，`30000/1001`）真实 PTS 偏移与尾帧边界**：
   - 在真实素材 `ocr_941.mp4`（`duration_ms = 30025`）上，均匀步长 5000 ms 生成的原始采样点包含 `30000 ms`（距容器总时长仅 `25 ms`，短于单帧持续时间 `~33.37 ms`），导致视频流在最后一帧（PTS < `30000 ms`）结束时触发 `PyAVMediaBackend.extract_frames` 严格的 `NO_FRAME_IN_RANGE`。
   - **修复决策**：保持 `PyAVMediaBackend.extract_frames` 对显式半开区间 `[start_ms, end_ms)` 与尾帧越界的严格报错不变（绝不借帧或伪造 PTS），而在应用层自动采样函数 `build_sample_timestamps_ms` 中增加 `tail_margin_ms = min(250, max(0, duration_ms - 1))` 安全尾边距。修复后 `ocr_941` 稳定抽取 6 帧真实 PTS `[0, 5004, 10008, 15012, 20016, 25020]`，且保留 `requested_ms != actual_pts_ms` 的如实记录。
   - **对 M2/M3 的指导**：M2 帧提取器与 M3 时间轴分段器必须假设真实视频的 `last_frame_pts_ms < duration_ms`（常见差值 `16–100 ms`），所有自动均匀采样点均须留出尾帧余量或按显式窗口回退而不伪造时间戳。

2. **无音轨视频与损坏文件的清晰区分**：
   - `ocr_941.mp4` 无音轨时自动走 `audio_status="no_audio"` 降级路径（0 次 ASR 调用，记录 `no_audio_stream` warning，继续完成视觉观察与 QA），而在 `test_slice_media.py` 中截断损坏文件明确返回 `CORRUPT_MEDIA`。

3. **Windows 平台 `pytest-socket` 离线隔离特性**：
   - Windows 上 `asyncio.run` 会初始化 `ProactorEventLoop` 内部 loopback socketpair，触发 `--disable-socket` 拦截。离线 CLI 与 `eval/slice_runner.py --offline` 在使用同步完成型 Fake Provider 时通过纯协程单步驱动避免创建事件循环 socketpair，仅在显式 `--live` 模式下进入 `asyncio.run`。

## 4. Fake vs Live 严格分离与诊断反作弊约束

`eval/slice_runner.py` 强制执行以下不可绕过的守卫（由冻结测试 `tests/unit/test_slice_report.py` 覆盖）：
1. 任何缺失固定题目（如丢弃失败题）或事后将 `answerable` 改为 `not_answerable` 的报告均直接抛出 `SliceReportError`；
2. `offline_fake` 报告声明 `is_live_quality_evidence=True`，或 `live` 报告中混入 `provider_mode="offline_fake"` 题目，均直接抛出 `SliceReportError`；
3. `offline_fake` 永远返回 `can_claim_model_quality=False`、`quality_gate_passed=False`、`decision="pause"`；
4. 运行器的 `--live` 需要显式输出目录、凭据和批准文件。文件中的 `live_enabled` 与 `cloud_egress_authorized` 须为布尔真，并至少指定一项数值限额。运行和报告合同见 §4.1。
5. Live 诊断门槛：可答题需达到 `ceil(0.75 * total_answerable)`（9 题中至少 7 题人工复核正确）、不可答题需 `100%` 诚实拒答（3/3）、引用合法率需 `100%`（低于 `100%` 直接 `pause`），且所有未通过题必须完整保留在 `failed_question_ids` 与 `failed_cases` 中。

### 4.1 2026-11-26 离线复核后的合同修订（待审核）

每份切片批准文件约束整次运行，包括所有视频的视觉请求和所有问题的 QA 请求。每个分析、问题仍使用自己的 M1 预算。发送前，两层限额同时生效。下例用于 `--offline --budget-config` 演练。

```yaml
live_enabled: false
cloud_egress_authorized: false
budget:
  max_model_attempts: 16
  max_submitted_image_parts: 20
  max_images_per_request: 8
  deadline_seconds: 180
  per_request_timeout_seconds: 30
  max_estimated_cost_usd: 0.10
```

例中的数字仅供演练。批准人按需填写限额，省略的维度继续受 M1 各任务既有上限约束。金额按配置价格估算。输入预留按提示词的 UTF-8 字节数加封装余量及图像额度计算，输出预留与两个适配器提交的上限同为 2,048 tokens。实际用量可用时结算估算值，计费或远端结果未知时保留预留估算及 `unknown` 状态。最终金额仍需与供应商核对。

报告写入 `m1.5-slice-report-v2`，评分器兼容 v1。评分时核对答复状态、主张、证据数、缺口与人工判定。整批引用数为零时，比率是 JSON `null`，决策为 `pause`。每道固定题都有 `completed`、`failed` 或 `not_run` 状态。错误行保留错误码及用量，失败运行另存到输出目录下的 `failed_runs/<run_id>/`。每次运行使用独立的分析 ID。逐题人工核对可使用单视频 CLI 或批量报告给出的 `evidence_manifest`，相对于当次 `--data-root` 打开本地证据文件。

## 5. 已知限制与未验证项（如实披露）

1. **已实测的范围**。官方模型元数据查询返回 HTTP 200，视觉与 QA 通过 16 次真实请求处理 3 段 D0。20 份图像、61,476 个输入 tokens、2,708 个输出 tokens，估算费用 0.0075016 USD。本次记录覆盖 `gpt-6-luna` 的这两种调用及配置。[OpenAI 模型说明](https://developers.openai.com/api/docs/models/gpt-6-luna)
2. **质量与时间边界**。人工确认了 5 道失分题，其中 4 道可答题被拒答，另 1 道遗漏所问剧情。原始证据中 `ocr_750` 的一个 ASR 段结束于 61,360 ms，超出片长 1,360 ms。观察、检索候选及答案对该段的引用均为 0。
3. **OS 级离线隔离未在当前宿主执行**：所有默认测试在 `pytest --disable-socket --allow-unix-socket` 下通过，但未在 Docker `--network none` 容器内复核。
